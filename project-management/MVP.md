# 单人 MVP 产品基线

更新日期：2026-10-29  
状态：Baseline v1.3，交互细化至D-126，D-127固定原生样本已验证所测控制/退队重排；全部原版内容、独立会话等目标保持，通用覆盖/量化预算仍待实验

## 端到端玩家闭环

1. 玩家安装并启用 Replay Mod。
2. 进入受支持的单人对局后，模组自动开始录制，不要求玩家在开局前手动操作。
3. 正常录制保持静默；关闭录制、启动/中途失败或进入明确不支持的场景时，玩家收到可理解的提示。失败或不完整记录不得伪装成完整 replay。
4. 主菜单提供与“单人游戏”“多人游戏”并列的 Replay 入口；进入后，Replay 在管理页中以角色、时间、seed、进度/结局等元数据自动标识，玩家可以选择记录、删除记录或打开所在目录。
5. 玩家也可以从管理页导入另一台机器传来的 replay。播放器先校验文件完整性、版本、模组环境与安全边界；不匹配或危险文件只给出诊断，不强制执行。
6. 通过校验后进入独立观看会话，不切换玩家用于正常游戏的 profile，不占用或覆盖现有 Continue 进度。默认使用分类 config 的压缩节奏，也可切换为原始节奏，并应用全局速度倍率。
7. 观看时可以暂停/继续、按玩家操作 Step、调速，并通过房间内操作时间轴及全局路线图向前或向后定位。
8. 播放状态出现可恢复偏差时，播放器用记录的权威状态自动纠偏、再次校验、继续播放并写结构化日志；不可恢复时停在最后可信位置并明确报错。
9. 玩家停止观看后安全退出观看会话并返回 Replay 管理页或主菜单；原 replay 仍是独立记录，既有单人进度与 Continue 入口保持原状，观看状态不会被转换为一局可继续游玩的普通游戏。
10. 玩家可以再次打开 replay，或通过文件复制把它分享给匹配环境中的其他玩家。

## 已确认的 MVP 产品要求

### REC-001：默认自动录制

- 模组启用后，受支持的单人对局默认自动录制。
- 玩家不需要为每局单独点击“开始录制”。
- 提供全局设置以关闭自动录制；具体设置位置和是否允许局内切换待设计。

玩家价值：值得保存的对局通常在进行中或结束后才被意识到，手动开启会造成不可恢复的漏录。

验收方向（尚待技术验证）：开始受支持的单人对局时自动创建录制会话；正常游玩无需额外确认；关闭设置后新对局不产生 replay 录制。

### REC-002：性能是发布门槛，完整单人覆盖是持续目标

- 自动录制不应对正常游玩造成明显影响；若首版覆盖与性能发生无法立即解决的冲突，优先守住性能门槛。
- 产品目标仍是尽可能覆盖全部单人场景，不把首版临时排除项视为永久范围。
- 内容覆盖目标明确包含受支持版本的全部原版卡牌（含升级）、遗物与药水，以及其自动触发、持续状态和联动效果；当前基础牌/指定遗物等实验限制不作为最终支持边界。按机制和实际场景分批实现/验证，不把少量代表样本成功写成全部内容已经支持。
- 未支持或未经验证的场景必须明确记录并继续补齐，不能静默宣称完整支持。

玩家价值：默认后台录制必须足够轻量才可长期启用；同时，玩家不能被迫猜测某类房间、事件或战斗是否会漏掉。

验收方向（尚待量化）：定义空闲与操作热路径的性能预算；维护单人场景覆盖矩阵；首版临时缺口有明确提示、文档和后续任务。

### REC-003：正常录制不常驻提示，只报告例外

- 正常录制时不在游玩界面常驻“正在录制”图标，也不实时显示文件大小。
- 录制关闭、无法启动、中途失败或进入明确不支持的场景时，应及时提醒玩家。
- Replay 管理页面是否展示文件大小属于 J4/存储管理设计，不由本条排除。

玩家价值：默认自动录制应安静、低干扰地工作，但玩家必须知道本局为何没有形成可信 replay。

验收方向（尚待交互设计）：正常成功录制不增加常驻 HUD；每类可检测异常都有清楚且不过度打扰的通知；失败 replay 不伪装成完整可用记录。

### LIB-001：首版 Replay 管理能力

- MVP 支持在管理页面删除 replay。
- MVP 支持打开 replay 文件所在目录。
- 自定义命名/重命名不属于 MVP；首版根据角色、时间、seed、进度或结局等已有元数据生成可识别名称。
- 自动名称的精确格式和删除确认/恢复策略待交互设计。

玩家价值：玩家可以控制磁盘内容并直接取得文件用于诊断或手动分享，同时避免首版投入非核心编辑功能。

验收方向：玩家能识别列表中的不同 replay；删除操作目标明确且有防误触设计；“打开所在目录”定位到正确文件。

### PLAY-001：MVP 基本观看控制

- 暂停与继续。
- Step每次加入一次完整玩家操作（出牌/用药/结束回合）的待播请求，连点累计；暂停只排队、按Play后执行业务，不改变运行门/连续开关。牌内选择原生展示并按录像自动回应，不单独消耗Step；暂停可浏览，Play继续当前未完操作。D-123操作级交互按D-127固定样本验证，一般覆盖未完成。
- 播放速度调整。
- 停止并安全退出 replay，不把当前观看状态转换成可继续游玩的普通对局。

### PLAY-SESSION-001：主菜单独立 Replay 会话

- 主菜单提供专门的 Replay 入口，产品层级与“单人游戏”“多人游戏”并列，而不是要求玩家先开始/覆盖一局普通游戏或切换到专用 profile。
- 打开 Replay 管理页和开始观看时，即使当前 profile 已有进行中对局，也必须保留原 `Continue` 进度。
- Replay 播放使用独立、非进度性的运行会话；不得把 replay fixture 写入普通 `current_run.save`，不得增加普通对局 reload 次数，也不得以切换玩家 profile 作为正式工作流。
- 停止、返回主菜单、播放失败和可合理测试的异常退出后，原进行中对局仍可从相同位置继续。
- “独立会话”描述产品可观察结果，不预先指定采用内存 store、Replay 专用 context、拦截保存或其他实现；具体机制必须经调查和实验决定。

玩家价值：观看 Replay 是主菜单中的独立功能，不会让玩家在“保留当前爬塔进度”和“观看回放”之间做选择，也不会要求理解开发用 profile 隔离。

验收方向：准备一个已有 Continue 的受保护 profile，记录其 save 身份和可见进度；打开列表、播放、停止、失败并重新启动游戏后，原 Continue 仍存在且内容不变。Replay 会话产生的文件只能位于明确的 Replay/诊断存储范围。

### PLAY-002：可配置的分类操作间隔

- 播放节奏不能只提供一个写死的统一间隔。
- 不同类型的观看停留应支持配置，例如两次出牌之间的停顿、选卡界面停留时间等。
- 录制文件保存玩家语义操作的相对时间戳。
- 默认播放采用分类 config 节奏，压缩玩家长时间思考或离开期间的空白。
- MVP 同时提供“原始节奏”模式，按记录时间调度玩家操作。
- 全局速度倍率作用于当前播放模式；具体分类、默认值和倍率组合规则仍待验证。
- 原始节奏只累计游戏处于聚焦、未暂停、非加载且玩家可正常交互时的时间；保留该状态下的真实思考时间。
- 暂停菜单、窗口失焦、加载画面以及可识别的模组/系统阻塞不计入原始节奏。

玩家价值：不同界面的信息密度不同；统一间隔会让简单动作显得拖沓、复杂选择又来不及观看。

精度边界：时间戳用于复现语义操作之间的节奏，不自动等于逐帧还原当时的动画、加载和渲染时序。播放器必须同时等待游戏进入可接受下一操作的状态，不能为了追赶时间戳而强行注入尚不能执行的操作。

### NAV-001：前进与后退是重要能力

- 产品需要支持有意义的向前和向后导航，而不只是暂停后继续顺序播放。
- MVP 目标包含三个层级：上一/下一玩家操作；上一/下一回合、房间或楼层等结构节点；点击或拖动时间轴定位到任意已记录操作附近。
- “后退”要求恢复过去状态；检查点加快速重演是优先验证的候选技术假设，不是已确定架构。
- 2026-10-26用户澄清：后退应直接呈现上一操作稳定点，不应每次重置对局、可见地从房间起点重新播放；仅遮住慢重播不能自动通过。DEMO-002已用观看期稳定点缓存验证一个样本的直接恢复/继续，但最终机制、支持范围与发布延迟仍须逐步确认，不等于任意内容导航完成。
- Counter-Strike demo 系统作为播放器心智模型参考，但不假定其基于 tick、网络状态和快照的底层方案能直接移植到 STS2。

### NAV-002：房间内时间轴 + 全局路线图

- 微观层：对局房间内使用时间轴表示已记录的玩家操作和结构标记，承担 Step、前进、后退和拖动定位。
- 宏观层：按照实际经过顺序绘制类似成绩结算页的路线图，用房间图标表示普通战斗、事件、商店、精英、Boss 等节点。
- 点击路线节点定位到相应房间/楼层；随后由房间内时间轴继续精确导航。
- 两层导航应同步显示当前播放位置、选中节点，以及无法可靠定位/回放的状态。
- 视觉参考：`evidence/product-references/run-history-route-reference-2026-08-24.png`。截图只规定信息组织方向，不锁定最终布局或美术。

玩家价值：长对局需要先按路线找到目标房间，再在房间里定位具体决策；单一的超长时间轴难以同时承担两种尺度。

### TAKEOVER-001：接管游戏不属于 MVP

- MVP 不允许从 replay 当前状态直接接管并继续这局游戏。
- 停止回放后仍保持 replay 是可重新打开、可继续导航的独立记录。
- 明确不采用 RunReplays 式不可逆转换：接管后 replay 变成普通对局且无法返回原回放。
- 未来若重新考虑，必须先定义为独立分支/练习会话，并解决返回 replay、存档隔离、成就、统计和新分支录制；本阶段不设计具体方案。

理由：接管不是观看闭环的必要能力，而且其产品语义和副作用尚未形成可信方案。不可逆转换会破坏 replay 作为稳定、可反复浏览记录的核心属性。

### STATE-001：强记录、自动纠偏并继续

- Replay 不只记录语义操作，还记录足以校验和恢复播放状态的额外权威状态。
- 目标是尽量在录制设计上避免不可恢复 divergence，而不是把偏差当成正常播放器分支。
- 播放发现状态偏差时，若存在可用的记录状态，应自动覆盖/恢复到记录状态并继续播放。
- 每次偏差与恢复都写入结构化诊断日志，至少包含 replay 位置、操作、expected/actual 摘要、恢复来源和恢复结果。
- 成功纠偏不要求中断玩家观看；replay/session 应保留“发生过纠偏”的诊断标记。
- 若记录状态因损坏、缺失类型、schema/API/资源不兼容而无法装载或恢复，必须报告不可恢复错误；不能声称强记录保证任意跨版本播放。
- 权威状态本身无法读取或恢复时，停止在最后可信位置并显示明确错误；这是不可恢复兜底，不是普通 divergence 的默认行为。

产品价值：播放器优先完成观看，而不是因可修复的小偏差停止；同时保留足够诊断证据定位实现问题和兼容问题。

技术边界：当前未决定完整快照、增量状态、状态指纹和检查点的组合与密度。它们必须与默认自动录制的性能门槛共同实验，不能通过每次操作同步写完整状态来换取表面可靠性。

原生时序风险：操作取消、抽牌触发和动画/Task交错可能使实际状态偏离单凭“同样操作＋seed”预测的路径。强记录应忠实反映实际执行结果，并评估必要因果事件/完成与取消边界；时间戳不单独保证调度复现。尚未指定逐帧或全动画记录架构，见[技术笔记](technical-notes/NATIVE-ANIMATION-TIMING.md)。

### VERSION-001：MVP 只承诺同一受支持版本播放

- 当前 MVP 目标构建为 STS2 public-beta `v0.111.0`。
- MVP 不要求在不同游戏版本上播放同一个 replay；版本不匹配时必须明确诊断，不静默尝试并宣称成功。
- Replay 从首版开始记录精确游戏构建、Replay 格式版本、启用模组/版本及可取得的内容标识，为未来兼容工作保留证据。
- 跨版本播放被定义为 MVP 完成后的独立大型目标，不是小修复或顺手任务。

产品价值：首版可以集中保证一个真实玩家版本上的可靠闭环，同时避免文件缺少关键元数据而永久阻断未来兼容。

### MOD-001：MVP 的其他模组兼容边界

- 正式保证范围为原版游戏内容、Replay Mod 及其必要依赖。
- Replay 始终记录录制时启用的全部模组及版本；能取得时同时记录稳定 ID、artifact/hash 和是否影响 gameplay。
- 播放环境的 gameplay mod 集合或版本与录制环境不一致时，必须明确警告或拒绝播放，不能静默当作兼容。
- 其他 gameplay mod 的正式兼容不属于 MVP，后续按具体模组或兼容协议逐步验证。
- 纯 UI/外观模组采用尽力兼容，不纳入首版保证；若实际影响 replay 状态或 hook，则按 gameplay/不兼容处理。

产品价值：先保证一个可测试、可解释的基础闭环，同时让模组不匹配可诊断，并为未来生态兼容保留证据。

### SHARE-001：同环境跨机器分享与安全导入

- MVP 的 replay 文件应可复制到另一台机器，并在匹配环境中通过 Replay 管理页导入和播放。
- “匹配环境”至少要求相同的精确游戏构建、兼容的 Replay 格式与 Replay Mod 版本，以及相同的 gameplay mod 集合和版本；不匹配时给出明确诊断，不强制尝试播放。
- 导入时校验文件类型/格式、schema、完整性、合理的文件大小以及版本和模组元数据；损坏、截断或不受支持的文件不得伪装成可用 replay。
- 外部 replay 一律视为不可信数据：不得执行文件携带的代码，不得接受其指定任意读写路径；解包和写入只发生在受控 replay 存储范围内，并防止路径穿越与覆盖现有文件。
- Replay 默认不保存分享所不需要的本机绝对路径、Windows 用户名等本地身份信息；确有诊断需要的敏感字段必须单独审查和脱敏。
- 本条不承诺跨游戏版本播放，也不承诺缺少录制时 gameplay mod 的环境仍可播放。

玩家价值：玩家可以把 replay 发给使用相同环境的朋友观看，同时让“导入别人发来的文件”具备清楚且可测试的安全边界。

验收方向：在两台等价环境之间完成导出/复制、导入和播放；覆盖正常文件、重复导入、损坏/截断文件、超限文件、版本/模组不匹配和恶意路径字段等反例。

## MVP 发布验收基线

下表定义产品上的通过条件。性能数值、导航延迟、检查点密度和文件大小上限必须由实验量化并经 Project Lead 接受后填入测试规格；在此之前不能宣称达到发布门槛。

| Gate | 最低通过条件 |
| --- | --- |
| G-01 自动录制 | 默认设置下，开始受支持的单人对局会自动建立录制；关闭全局开关后，新对局不录制。 |
| G-02 性能 | 空闲、地图操作、卡牌结算等已定义场景均满足经批准的平均开销和最长 hitch 预算；不接受仅凭主观“感觉流畅”。 |
| G-03 场景覆盖 | 有版本固定的单人覆盖矩阵；所有宣称支持的战斗、事件、商店、奖励、选卡、地图与结局场景均有录制和播放证据。未支持项明确可见。 |
| G-04 文件与管理 | Replay 能在异常退出风险下保持可识别的完整/不完整状态；管理页可识别、删除和打开目录，不误删相邻记录。 |
| G-05 基本播放 | 同一受支持环境中，replay 可加载并完成已声明场景；暂停/继续、逐操作 Step、调速和停止均有稳定语义。 |
| G-06 双向导航 | 上一/下一玩家操作、上一/下一结构节点及时间轴定位均能到达正确状态；房间内时间轴与全局路线图位置一致，并满足经批准的定位延迟。 |
| G-07 播放节奏 | 分类 config、原始节奏和全局倍率组合行为可预测；原始节奏保留活跃思考时间，排除已定义的暂停、失焦、加载与可识别阻塞。 |
| G-08 状态可信度 | 注入的可恢复偏差会被检测、恢复、再次校验并继续；不可恢复状态会停在最后可信位置、提示玩家并留下结构化日志。 |
| G-09 版本与模组边界 | 精确构建、Replay 格式及模组环境进入元数据；不匹配环境不得静默播放。正式兼容矩阵限于已声明范围。 |
| G-10 分享与导入安全 | 匹配环境间可跨机器导入播放；损坏、超限、未知格式、路径穿越和任意载荷等反例被安全拒绝，且文件不泄露非必要本机身份信息。 |
| G-11 独立播放会话 | 主菜单有与单人/多人并列的 Replay 入口；打开列表、播放、停止、失败和重启均不切换玩家 profile、不写入或替换普通进行中对局，原 Continue 保持可用且内容不变；原 replay 可重新打开。 |

## 由产品基线导出的技术问题

- v0.111 上哪些低开销 hook 足以覆盖单人对局的语义操作、结构节点、初始状态和 RNG？
- 最小录制路径的平均开销、最长 hitch 与写盘行为是多少，发布预算应定在何处？
- 哪些状态属于恢复所必需的权威状态；指纹、完整检查点和增量状态应如何组合？
- 检查点恢复加快速重演能否同时满足逐操作后退、跨房间定位、确定性、文件大小与延迟要求？
- v0.111 是否存在可从主菜单建立的 Replay 专用 run/session context，使 `RunManager`、save store、reload count、统计/成就及 scene teardown 与普通 Continue 隔离？
- RitsuLib 的主菜单/运行时 UI、生命周期、补丁、设置、诊断和临时数据 API 中哪些可降低实现成本；哪些并不提供游戏运行状态隔离？
- 游戏聚焦、暂停、加载、可交互和系统阻塞能否可靠且低开销地识别？单个语义操作时间戳是否足够？
- Replay envelope、完整性机制、大小上限和受控导入目录应如何定义？
- 哪些 RunReplays hook/command 可作为候选或反例，哪些与 v0.111 已不兼容？

实验顺序与每项退出条件见 `EXPERIMENT_PLAN.md`。

## MVP 后方向优先级

当前产品排序为：

1. 多人 Replay。
2. 跨版本播放。
3. 从 Replay 创建隔离的可游玩分支，并能返回原 Replay。
4. 其他 gameplay mod 的正式 Replay 兼容。

该排序表达 MVP 完成后的战略优先级，不改变当前 MVP 仍为单人、同版本、原版 gameplay 内容的边界。尤其是多人 Replay，在进入实现前仍需独立调查权威状态、双方操作、网络事件、隐私、断线与同步模型。

## 待确认

- 游戏焦点、暂停、加载、可交互状态及模组/系统阻塞能否被低开销且可靠地识别。
- 双层导航的具体布局、路线节点元数据和不同分辨率下的交互形式。
- 检查点实现和 divergence 处理。
- 强记录的状态范围、密度、压缩/写盘方式、恢复语义和性能/文件大小预算。

## 当前明确非目标

- 多人 replay 不属于当前 MVP。
- 从 replay 当前位置接管并继续游戏不属于当前 MVP。
- 跨游戏版本播放同一个 replay 不属于当前 MVP。
- 其他 gameplay mod 的正式兼容不属于当前 MVP。
- 不以 fork RunReplays 并直接演进作为产品实现前提。
