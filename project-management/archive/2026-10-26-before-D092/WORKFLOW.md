# Project Lead / Implementation 协作工作流

更新：2026-10-26。适用于新签发工作包及明示续跑；不追溯改写旧实验。

## 目标与当前瓶颈

项目仍处于技术假设验证，不是功能堆叠阶段。ticker/readiness、A5初始重建、001B操作链与DET-001真实RNG单样本已验收。当前瓶颈是建立不受诊断污染的录制性能测量，再为强记录恢复/后退提供成本依据，不是重复同一重放样本或增加管理材料。报告、合成测试和探针编号数量都不是进度指标。

受控direct-write isolation、owner-fault/normal-restart、初始重建和实际操作轨迹各有局部证据；仍不构成完整独立Replay会话，也不降低不占用正常Continue的产品要求。

## 旧流程的问题与改法

1. **风险对象混淆。** 将可消耗的 modded 测试槽、account 设置、原生 diagnostic replay 和个人连胜存档套入统一“不许变化”规则。现在只将 unmodded profile1 作为个人进度保护目标；测试槽按具体假设管理，准备、业务、退出写入分别判断。
2. **探针缺陷升级成研究项目。** floor placeholder、Ready timeout、oracle aliasing 等已定位的 harness bug，常被迫经历停止、另写调查、另建探针。现在终态结束一个 attempt；允许在工作包的有限授权内修复同一 lineage，并使用新 attempt 保留证据。
3. **离线覆盖偏重数量而非可达性。** 简化假对象能通过，不证明完整实际路径满足前置条件。关键 gate 必须有实际前驱 schema/fixture 的完整正向路径，外加针对失败的回归测试；Godot/STS2 真实生命周期仍须 runtime 验证。
4. **自然步骤切碎，管理成了关键路径。** 配置、安装、启动、诊断和纯 harness 修复应放进一个窄工作包，逐阶段验收，不为每个复选框重新发任务。静态 INV 仅用于确有未解技术问题、且有明确决策价值的情况。
5. **过度重启实现上下文。** 同一 probe/milestone 优先由同一 Implementation 对话负责；新对话用于新职责、独立审查或明显不同的任务线，不按每个 INV/SPIKE 强制重开。减少重复恢复上下文可能降低开销，但不保证每次 token 更少或错误更少。

上述流程问题主要来自 Project Lead 的任务切分和权限设计，不能把遵守过严工作包的实现者当作根因。

## 分工与持久化

- Project Lead 维护 CURRENT_STATUS、TODO、DECISIONS、路线与工作包，独立验收关键证据，不主要实现源码。
- Implementation 是当前任务源码/报告的单一写入者；完成后提交报告、证据索引、明确结论与下一建议，不擅自宣布产品 milestone 完成。
- 每次接任务只读当前状态、当前工作包、直接依赖证据；按需要索引历史，不反复完整重读所有历史。
- 一个工作包原则上只有一个业务假设、明确成功/停止条件、实现者权限、人工测试请求及结果证据。不要重复粘贴所有历史规约；引用本文件与 TEST_PROTOCOL，写清必要例外。
- 对话只是工作上下文，不是项目长期记忆。结束时用简短 handoff 记录已确认、未知、决策变化、下一任务。
- 2026-10-09用户明确给予持续授权：本项目内，PM可直接向已有Implementation对话发送工作包、跟进、修订要求与验收反馈，无需逐次再问。授权原话为“你直接执行就可以。以后都可以直接授权”。每次仍记录目标对话和任务范围；不扩展到其他项目、创建新用户对话、额外个人数据权限或自行操作游戏。工具可用本身仍不是授权来源。

## 可修复失败与真正阻断

- 首个终态停止**本次运行**，保留 artifact、源码版本和日志；不能覆盖证据、在旧 attempt 继续业务或把 FAIL 改写为 PASS。
- 新工作包可授予 harness-only repair envelope，包括已建立实验基线后的 observer/readiness/deadline/证据框架缺陷。不能仅因已有 baseline 就禁止一切修复。
- 修复必须定位到 harness，保持生产行为、问题和验收语义不变，补有区分力的回归测试。新 build/new attempt；如基线已失效，只能为新的 attempt 重建，不抹掉旧窗口的差异。
- 默认建议预算：初次正式 runtime attempt，加至多两次针对已定位 harness 缺陷的修复后重测。具体工作包可收紧；配置会话不是正式业务 attempt，但也不得无限循环。
- 涉及 unmodded profile1、生产 Task/行为被修改、未知副作用、结论不明且无法安全区分、假设/验收变更或预算用尽时，交回 Project Lead。真实 production FAIL 不能伪装成 harness failure。
- 旧工作包永久停止的 probe 不因此复活；当前授权只适用于明确列出的新/在研 lineage。

## 测试层次与验证比例

先用现有固定 DLL/IL、fixture、.NET tests 解决能离线回答的问题；必要时单独验证 Godot 生命周期。正式 STS2 无头能力仍未形成已验证安全工作流，不能默认可自动跑局。真实游戏测试由用户手动操作，Codex 构建、安装授权文件、读取范围受限日志和分析证据。

版本未变且封存候选 hash 相同，不重做已经验收的全套离线调查。代码改变后，执行相关回归、Release build、受影响的 patch/非干扰审计；关键边界改变才扩大验证。

001B收尾经验：把一次性配置/精确文件变更与可重复只读后置核验分开。变更已完成、核验脚本失败时先确认实际后置状态，不重放变更脚本。外部manifest读取统一考虑UTF8 BOM；检查有效(id,source)开关关系，不把disabled记录被正常化或缺失本身当作checkpoint变化。是否补记录仍依具体包的范围授权，不恢复整个settings或扩大为旁支调查。

实验用可消耗槽不等于正式产品允许破坏存档。诊断不要强行承担 isolation/crash/reconstruction 三种证明；各自只作其证据足以支持的结论。

准备次数与正式Arm预算分开。用户已明确允许有限批次重开时，在同一进程正常回主菜单/新建局，不强制每局退出整个游戏、重新配置或逐局审批；批次有上限，到合格目标/异常立即停止。纯准备规则更新不要求新候选、重跑未变测试或新建INV。

未Arm/CP前的准备重启不自动等于业务失败。工作包明确允许时，可用当前进程自身启动事件/身份和用户本次启动确认补齐来源，再在当前attempt开始正式窗口；不拼旧进程gate或追认准备步骤全部合规。关键账号/Cloud/对局来源或未知副作用不能省略，次数可如实记约数/Unknown。已有Arm/CP或真实数据差异不适用这种准备恢复。

把旧退出根因未知与当前输入/状态不可信分开。旧进程设备丢失等已保留日志marker，不单独要求先完成硬件/平台根因调查再测新fixture；当前来源/状态门仍须通过，不证明旧进程零写入、绝对无害或crash recovery PASS。当前异常、身份不符或正式窗口差异仍按原停止规则。

## 本轮安排

多次人工输入回传但无接收证据时，停止反复试键，先检查最新输入，再补最小可区分harness观察，不把缺记录当资格失败。新增准备Continue来源须exact hash/模式/单次绑定并与正式B隔离，做一次增量离线验收，不全局关门或另建泛化INV。

A5/001B/DET-001保持关闭。2026-10-26 D-091验收PERF Phase0，下一步同包Phase1独立候选的离线build/合同/非干扰验证，延用原Implementation，不重建旧探针、不安装/配置或请求runtime。三模式保持同modded上下文，不能零模组启动进入个人槽；空壳不冒称零观察基线，代理不当FPS/稳态。未经变化的旧测试/计时不重复，sealed原交付不改；另一账号排除。
