# 以Seek为基础的回放架构评估

初稿2026-10-28，更新2026-10-29。D-119已确认基本导航体验并启动[SEEK-001](../handoffs/SEEK-001.md)验证可续播状态/统一原生前进；本页的最终架构与缓存策略仍属候选。旧PLAYBACK-001停放，003未反馈结果仍Unknown；新包已解除讨论HOLD，普通迭代不另审批。

## 用户提出的路线

把Back视为Seek的一个特例，最终支持跳到任意位置；在可恢复状态点基础上，前进统一使用原生业务与动画。跳转时直接恢复/刷新，省去“首次原生、历史另模拟显示”的双路径。用户提出提前计算并储存各状态点，本页评估其来源、粒度与代价，不默认承诺整场预计算或逐毫秒快照。

## 当前事实

- 现有默认格式4—6路线：首次前进原生执行；历史前进恢复数据并播放本次观看捕获的显示轨迹。普通Stable在Finish(settle:true)后发布节点；窄lookahead在下一动作执行前同步捕获中间数据。
- DirectCheckpoint/IdentityMemento保存选定数据与容器、保留原对象身份，排除Task/Delegate/GodotObject等。Restore要求同一run/combat/turnState；它不是任意独立进程/新房间都能恢复的通用存档。
- 早期DEMO-002直接稳定点路线已有恢复后重新原生执行的局部证据，包括所测跨EndTurn；STATE-001有首Defend文件冷恢复/纠偏后原生继续至胜利证据。这支持可行性，不能外推选择挂起、新单位/死亡任意阶段、所有角色/文件点。
- 原生ActionExecutor按队列await动作，并有NonInteractiveMode执行分支；NonInteractiveMode受TestMode/AutoSlayerCheck影响。CardPileCmd仍存在场景/Tween访问。只是快速逻辑/离屏预计算线索，不能视为完整可用的后台引擎。INV-012也未证明正式release有可直接运行的自动无头CLI。

## PM推荐的候选结构

以“可恢复且可续接原生执行”的状态点为核心，展示是原生执行产生的消费者。每个语义操作/选择点有稳定索引、原始时间与状态对应关系；逻辑完成、输入接受和动画尾部结束分别表达。Seek选择目标或前置状态点、退役旧上下文、恢复数据并建立正确的新执行/选择上下文、刷新显示，再通过原生路径继续。Back只提出较早的Seek请求，不建另一套倒播业务。

原生代码自身含显示await与选择依赖，目标是消除mod额外的普遍展示门槛、统一路径，不是承诺原生业务和动画能完全抽离。复用原生模型/命令可减少重复实现牌效/显示，但OO本身不自动解决序列化、对象身份、订阅和异步续接。

## 主要收益与代价

| 方面 | 潜在收益 | 难点/代价 |
| --- | --- | --- |
| 前进 | 首次与退后重做复用原生命令、牌效、遗物和动画 | 恢复后的执行器/回合循环/选择宿主必须正确，旧Task不能序列化后复活 |
| 跳转 | Back、跳楼层、时间轴统一为定位与恢复 | 稳定逻辑点与动画中途/选牌挂起点难度不同，任意毫秒恢复尚未证明 |
| 覆盖 | 减少历史专用显示复制与逐细节修补 | RNG全状态、生成卡/单位身份、模型成员与订阅仍须恢复；跨场景需不同恢复入口 |
| 强记录 | 用录制当时的状态核对/纠偏原生重演 | 重演预计算只是缓存；偏差时它也会算错，不能替代录制时权威事实 |
| 提前建索引 | 未访问位置也能定位，重复Seek更快 | 整局预计算可能慢、占内存/磁盘；Godot主线程/全局单例限制不能靠Task.Run绕过 |
| 正常录制 | 当场采集状态避免观看时重新计算全部 | 同步捕获/复制开销需要实测，后台写盘不能消除主线程冻结状态的成本 |

## 状态来源与缓存策略

建议逻辑上区分三个部分：原始语义操作与时间、录制当时的权威状态/核对事实、可重建的Seek索引缓存。原局发生引擎bug而重演未复现时，重演生成的所有状态仍可能偏离原局；必须保留原始权威依据和诊断/纠偏规则。

完整可恢复状态可以在原录制中捕获，也可以在观看时按需/提前重演生成缓存；后者要通过原始事实验证。存储可用全量+增量/共享数据，也可稀疏关键点+有限前向重演，不要求每一步保存整套相同对象。具体取舍由真实捕获成本、文件体积、Seek延迟决定，未测量前不指定频率或承诺每步毫秒级。

“支持任意时间定位”的产品目标可以保留，内部不必每毫秒都有可续接存档。事件点可直接恢复；事件之间可以从前一可恢复点正常推进至目标时刻。帧级准确暂停/特效恢复、原始节奏映射及选择窗口内部续接仍是待验证内容，不能把吸附到最近事件冒充已完成任意时间Seek。

## 当前验证方向（SEEK-001）

先验证现有数据恢复后能否在新鲜、正确的执行上下文中继续原生命令，优先跨回合与选牌宿主这些尚缺的关键路径；不重复只证明两张防御，也不先序列化整个游戏或构建全局无头平台。然后用一小段录像验证未访问位置的索引/Seek、原生续播和结果等价。已有可用版、原片与实际证据保留；若候选成立再逐步迁移历史展示，不先删除当前实现。

## r1实测后的判断（2026-10-29）

SEEK-001/build-002已在固定猎人4宿主片段取得恢复后原生续播证据：Implementation摘要1070事件/3次打开、41次原生宿主结果-RNG核对、38次新选择上下文与提交、22次Seek到达匹配；退出manager/所比较Continue进度恢复。用户称基本符合预期，同时报告手牌显示/选择Seek等待和队列继续问题。不认全视觉/交互、完整战斗或通用Seek通过；PM读摘要/报告与关键源码，未逐条重计原事件。

| 问题 | 分类 | 结论 |
| --- | --- | --- |
| 选牌Seek后手牌异常 | 具体代码缺陷的高可信解释 | 重建时隐藏NRun，原生ActiveHolders依赖IsVisibleInTree，空集合使布局跳过；保留逻辑可见性的遮挡/选择布局校正是候选，尚未修复实测。不是恢复后原生前进必然失败 |
| 稳定点约9–83ms，第二弃牌窗口约1.86–1.94秒、已选状态约2.40秒 | 当前恢复策略成本 | 应用数据约9–81ms；选择目标需要重建牌效与前一选择，原生显示/等待仍发生。多存数据不自动等于能续接旧程序位置 |
| 从暂停的选牌窗口跳到稳定点也慢 | 旧上下文退役成本 | 一次约1865ms中1791ms在收完旧Survivor，数据应用约25ms；缩减目标选择粒度不能消掉从选择源点离开的成本 |
| Pause丢有限Step请求、恢复变无限播放 | 控制模型/规格细化问题 | 之前混用了导航预算与已原生入队卡牌的“等待继续”；需要明确区分有限请求、连续播放及暂停状态，不是原生牌效架构必然限制 |
| 三击生存者没有多牌排队动画 | 本切片未覆盖该能力 | 三节点在同一张牌的选择内部，当前一次一手动宿主；不得算多原生手动牌排队已验。未来可复用已录铁甲两防御片作新路线最小片段，不回滚旧矩阵或要求重录 |

建议保留已取得证据的统一原生前进主干，不据本轮现象推倒重来或删去选择节点。当前代价可分为旧宿主退役、数据应用、目标宿主重建、显示刷新；若要近即时选择Seek，需证明可取消且隔离的旧上下文、有限快速推进或可续接选择状态，不能只删await/取消Task后应用数据。尚不保证这些改造成本低。

D-120优先保留精确选择Seek/原生续播，先修布局/控制，短等待暂接受，不改快速退役/重建。D-121最终定义运行门、连续开关、有限余量独立：Step只排队，暂停时按Play后才执行；Pause保留模式/量，Play只恢复，Seek/Back清旧路线并暂停。连续关且量耗尽时等待新请求，运行门不暗改。产品确认不等于真实多牌原生入队已实现。本次未改代码/DLL/派新测试。
