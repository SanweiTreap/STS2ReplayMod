# 整局Replay外壳与非战斗房间规划

2026-10-30起草，2026-10-31阶段收束更新。状态：首批RUN-001已按代表样本DONE_WITH_LIMITATIONS，保留006，结果见[报告最新摘要](../investigation-reports/RUN-001-report.md)。原始需求是承载路线、问号/火堆/宝箱和跨层的大外壳；首条非战斗闭环已验证，后续房间仍为规划，尚未派发。

## 当前有什么，还缺什么

2026-10-31阶段更新：CONTENT-006/009已按代表样本验收，Replay RunId、局内战斗/attempt、幕/楼层元数据、Continue跨进程关联、战斗列表及三鼠召援录播/恢复均有实际证据，边界见CURRENT_STATUS。它是整局归属的地基，不是完整路线日志/整局播放器；RUN-001在此基础上推进。

当前非战斗影响由下一场真实checkpoint承接：能知道下一战实际带了什么牌/资源，却不能据此还原战后选了哪些奖励、选路、营火休息/升级、宝箱取舍或事件选择。战斗文件按局分组不等于这些决策已有记录；旧片也不能无证据补成完整路线。

## 建议的组织方式

逻辑上按“整局记录 → 按真实访问顺序排列的房间 → 各房间内的操作/结果”组织。战斗是房间的一类，已有战斗文件成为该房间的内容，不要求把所有数据塞进一个巨型JSON。

- 整局层：记录环境/角色/seed、稳定局身份、Continue与attempt关系、实际进度/结局/缺失范围，协调房间切换和观看会话退出。保留普通Continue隔离目标。
- 路线层：独立的房间访问身份和全局访问顺序，记录幕、幕内楼层/坐标、地图节点标记与实际房间类型；战斗序号不充当房间序号，幕切换也不以楼层复位混淆旧节点。重复加载/重试与真实新增访问分开。
- 房间层：战斗、营火、宝箱、商店、事件及奖励流程各沿原生入口记录语义决策、实际结果和必要状态；按共同生命周期接外壳，不为每个房间复制播放器，也不先造未验证的泛用类框架。
- 播放层：整局位置统一关联房间内位置。顺播逐类执行已接通的原生流程；显式跨房间定位从已证明可恢复的起点加载。未支持房间可显示路线与缺口，不能跳过其操作后宣称已经完整播放。

固定源码RunManager.EnterMapPointInternal在创建房间时分别保存地图pointType、实际abstractRoom.RoomType和ModelId，问号有RollRoomTypeFor；事件还可承载内部CombatRoom/ParentEventId。因此不能只记一个地图图标、假设一个坐标永远对应一种界面，或把问号房间都归成同一种事件。应沿实际发生的原生生命周期记录，内部阶段/子房间的具体结构待实施验证。

最初可沿现有列表展示“路线节点＋其中可打开的战斗”，随后再做产品既定的成绩结算式图标路线；数据归属与真正房间播放先跑通，不先投入美术。布局不是当前需定死的架构。

3. 在同一骨架逐类接宝箱、商店、问号中的事件分支及嵌套战斗；跨幕先在数据中明示过渡，真实换幕/地图生成/房间加载与回放另取样验证，不因记录了Act就宣称播放已支持。跨房间导航在真实可恢复起点上渐进接入。

用户已批准第2项的RUN-001首批实现，第3项仍为排序建议，不扩大CONTENT-006旧结论。原生房间生命周期/决策/恢复的不确定性在可用链中直接验证，普通问题同任务修，不先恢复串行INV/审批链；跨幕验证留后续。

## 验收要回答的业务问题

- 同一局的路线顺序/实际房间/重试/Continue是否一致，非战斗节点没有被丢掉或冒充战斗；旧记录的缺失是否如实显示。
- 实际选的奖励和营火行为能否原生重现，并让下一场牌组/遗物/药水/HP/金钱/RNG相符，而不是直接载入后场状态冒充播放了前面的决策。
- 看早期房间或切换房间后，当前普通Continue和观看隔离/清理是否保持；不能用开发备份代替成品正确性。
- 新增记录的文件/内存/操作热路径开销是否可接受；不为路线展示逐帧读取整个录像库。

每类房间可用的checkpoint时点、选择/取消与奖励顺序、完整权威状态及恢复粒度仍未知；这是验证任务，不假定原生SerializableRoom能天然保存任意界面中间态。当前仍不提供选择页独立Seek，不复活旧Task/TCS。
