## 建议的组织方式

逻辑上按“整局记录 → 按真实访问顺序排列的房间 → 各房间内的操作/结果”组织。战斗是房间的一类，已有战斗文件成为该房间的内容，不要求把所有数据塞进一个巨型JSON。

- 整局层：记录环境/角色/seed、稳定局身份、Continue与attempt关系、实际进度/结局/缺失范围，协调房间切换和观看会话退出。保留普通Continue隔离目标。
- 路线层：独立的房间访问身份和全局访问顺序，记录幕、幕内楼层/坐标、地图节点标记与实际房间类型；战斗序号不充当房间序号，幕切换也不以楼层复位混淆旧节点。重复加载/重试与真实新增访问分开。
- 房间层：战斗、营火、宝箱、商店、事件及奖励流程各沿原生入口记录语义决策、实际结果和必要状态；按共同生命周期接外壳，不为每个房间复制播放器，也不先造未验证的泛用类框架。
- 播放层：整局位置统一关联房间内位置。顺播逐类执行已接通的原生流程；显式跨房间定位从已证明可恢复的起点加载。未支持房间可显示路线与缺口，不能跳过其操作后宣称已经完整播放。

固定源码RunManager.EnterMapPointInternal在创建房间时分别保存地图pointType、实际abstractRoom.RoomType和ModelId，问号有RollRoomTypeFor；事件还可承载内部CombatRoom/ParentEventId。因此不能只记一个地图图标、假设一个坐标永远对应一种界面，或把问号房间都归成同一种事件。应沿实际发生的原生生命周期记录，内部阶段/子房间的具体结构待实施验证。

最初可沿现有列表展示“路线节点＋其中可打开的战斗”，随后再做产品既定的成绩结算式图标路线；数据归属与真正房间播放先跑通，不先投入美术。布局不是当前需定死的架构。

### 用户经验补充：战外SL回到哪里

2026-10-31用户凭经验确认：商店退出重进会完全回到进入商店前；宝箱同样；问号除包含战斗的情况外，会回到进入节点前。这是用户报告，尚非本项目runtime验证。下一批据此优先把这三类建模为“从房间前存档锚点重新进入的新尝试”，不把前次已完成购买/开箱/事件选项当作已经持久化并继续追加。

例如买A后读回商店前、再买B：旧尝试仍保存，但最终延续路线只执行B；重做完全相同操作也属于新尝试，不按内容去重。测试应核对重进的金币/牌组/遗物/商品或箱子/事件阶段是否与实际保存起点相符，并确认最终模式不会多扣一次钱或多领一次。问号类型/商品/开箱结果是否相同及相关RNG仍需实际核对；“回到节点前”本身不能证明会重新掷成不同结果。

包含战斗的问号单列：事件选项前、内部战斗未完、战斗已完成/奖励、回到事件等阶段的持久化边界仍未知。保留事件父子房间关系，按实际load恢复位置确定继续还是新尝试，不统一强制回事件第一页，也不沿用普通已完成地图战斗的结论。

### 已接受的播放方向（D-137）

用户提出两种“可能的播放方式”都作为可选项，可以先实现一种。PM选择先做“最终实际延续路线”：默认沿最后采纳的尝试继续，原始失败/退出/读档前尝试完整保留，后续供“按真实时间播放全部经历”使用。同一份事实记录供两种播放策略使用，不录两份不一致的历史。第二种模式尚未实现；退出/启动等待的具体展示以后再定。

### 重复操作需要分别处理

1. Hook重复回调：同一次原生业务只记一次，以实际操作生命周期关联，不按文本/结果相似去重。
2. 真正重复行为：同名商品、相同选项、相同出牌也可能是不同的有效操作，必须保留身份、顺序和前后状态。
3. Continue未回滚：若载入状态已经包含已购/已领取结果，只接后续操作，不能重新购买/领奖。
4. Load回到更早状态：把新尝试连接到实际恢复的存档/录制位置，旧尝试保留但退出最终播放路径；例如“存档→买A→读回购买前→买B”，最终模式只执行B，完整经历模式保留A/读档/B。
