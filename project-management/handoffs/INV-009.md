## 必须回答的问题

1. `RunManager.SetUpReplay` 返回时，`RunManager.RunLobby` 按 production 方法体应为何值？完整追踪 `InitializeRunLobby`、其构造/分支、`NetReplayGameService` 能力与赋值点。
2. 从 `SetUpReplay` 返回到 `Launch` 前，哪些 production 或 probe 调用可能将 RunLobby 置空、替换、dispose，或使 getter 返回 null？区分确认不存在与尚未找到。
3. `RunManager.CleanUp(true)` 对 RunLobby unsubscribe/dispose 的精确分支条件是什么？当 RunLobby 为 null 时，跳过两步是预期无资源可清理，还是留下其他对象/订阅/服务引用？
4. R4 的实际 13-step reached set 是否与 setup-fault 点的正确 production path 精确一致？不能仅以“最终 state null/manager restored”替代资源义务证明。
5. 对以下两个边界分别列出 cleanup step：
   - `SetUpReplay` 完整返回、Launch 前的 setup owner fault；
   - Launch 返回且 NRun 安装、GenerateMap/room/frame/action 前的 post-launch owner fault。
   每一步标记 `Unconditional`、`Conditional(condition)` 或 `Not applicable`，并给出方法体证据。
6. 若两阶段义务相同，必须用证据证明；不得因复用方便而继续使用固定 15 步。
7. 给出且仅给出一个最终分类：
   - `ACCEPT_PRODUCTION_CLEANUP_WITH_REVISED_ORACLE`
   - `CONFIRMED_PRODUCTION_CLEANUP_DEFECT`
   - `INSUFFICIENT_STATIC_EVIDENCE`
