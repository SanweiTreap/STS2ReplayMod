## 唯一目标

给出一份足以让 Project Lead 安全签发或拒绝下一 fault/restart runtime matrix 的最小生命周期契约。必须回答：

1. transaction owner 从 timing gate、candidate 构造、override 安装、`SetUpReplay`、scene launch/ready、fault、finally、`CleanUp`、override clear 到主菜单重建的精确控制流与 ownership。
2. setup fault 的最晚安全注入点：必须已证明 state/override 路径真正建立，但尚未把实验扩大到 scene/action/reward；注入由 probe owner捕获，并必然进入唯一 finally。
3. post-launch fault 的最早充分注入点：必须证明目标 scene/run 已进入需要 teardown 的状态，但不要求完整渲染、quiet frames、玩家输入、dispatcher或自然胜利。
4. 两个 fault 点各有哪些 production task、deferred callback、scene continuation、run save task、synchronizer或 observer可能在 finally 前后仍存活；哪些可等待、取消、观测，哪些仍不可证明。
5. ordered teardown 的必要顺序和每一步可观察后置条件；特别区分 isolated task、`RunManager.CleanUp`、override clear/original manager restore、original task、scene/main-menu rebuild和terminal artifact seal。
6. restart check究竟能证明什么：前一 fault phase安全teardown并正常退出后的新进程验证，与“override活跃时强制杀进程/崩溃恢复”必须分开。判断首轮是否需要后者；若不需要，明确延期理由。
7. 下一运行矩阵应是一份工作包中的几个独立 fresh-process phase，还是多个工作包；为每个 phase定义独立不可覆盖 artifact/recovery、prior-integrity、人工动作、首个 terminal停止与跨进程衔接规则。
8. 哪些 boundary/side-channel 可沿用007A observer，哪些在异常窗口必须新增或不能可靠观察。不得用“所有外部副作用均被覆盖”替代逐项证据。

## 必须形成的运行契约草案

若静态证据足够，报告附上一张有限矩阵，至少逐行列出：

- 精确注入点和注入异常类型；
- 注入前必须成立的固定布尔条件；
- 禁止发生的业务动作；
- 需要等待/观测的 pending work；
- teardown 顺序与每步成功条件；
- protection、Continue、manager/run/scene 与 boundary 验收字段；
- artifact/recovery identity；
- PASS、FAIL、BLOCKED 与停止条件；
- 是否要求用户退出并在下一进程做 restart verification。

契约必须保留现有测试纪律：固定 modded profile1、不得读取其他 profile、Steam Cloud 状态只按可观察证据表述、游戏由项目发起人手动运行、Ready 后不得以人工响应 timeout 判失败、目标后不出牌/不领取奖励/不操作 UI。

- 不启动、控制或截图游戏；不使用 Computer Use。

## 唯一最终建议

只能选择一个：

- `READY_FAULT_RESTART_MATRIX`：静态证据足以签发有界运行矩阵；
- `NEED_NARROW_LIFECYCLE_PROBE`：仍缺一个不注入 fault、不安装新 transaction 的最小运行时生命周期事实；必须只描述该事实；
- `STOP_REASSESS_TRANSACTION`：发现无法约束或恢复的生命周期边界，当前全局 transaction 候选不应继续。
