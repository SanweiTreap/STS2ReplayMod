# INV-005：SaveManager 启动期 mutation 与保存调度调查

> 历史状态（2026-09-11）：本调查已验收，唯一建议为 `REVISE_WITH_TIMING_GATE`。下一任务为 `SPIKE-INV005A`；不得在 INV-005 范围内实现或运行 probe。详见 `project-management/investigation-reports/INV-005-report.md` 与 D-035。

任务类型：纯静态技术调查

## 任务目标

在固定 v0.111.0 程序集中，建立从 production `SaveManager` 创建/初始化，到 `NMainMenu._Ready` 与模组主菜单诊断入口可用，再到正常退出之间的窄范围调用图。识别 Settings、Prefs、Progress 的内存 mutation、同步/异步保存、未等待 task、deferred callback 与退出 flush，判断 live-seeded manager snapshot 是否存在一个可证实的 quiescent capture boundary。

本任务不要求复原 SPIKE-INV004A 当时具体哪个 JSON 字段不同；它要回答的是：历史 disk/live 瞬态差异可能由哪些 production 路径产生，以及下一 direct-write sentinel 能否可靠避开尚未完成的真实-store writer。

## 必须回答的问题

### A. Production 启动时序

1. 哪个 production entry 创建真实 `SaveManager`，以什么 store、profile id 和同步/异步选项创建？
2. `InitProfileId`、`InitSettingsData`、`InitPrefsData`、`InitProgressData` 的精确调用顺序是什么？调用者是否逐项 await，还是存在 fire-and-forget/task continuation？
3. 哪个事件或 await boundary 之后创建/显示 `NMainMenu`？`NMainMenu._Ready` 与模组注入的 peer-entry callback 在 production startup sequence 中处于哪里？
4. 主菜单可见是否足以证明 save initialization 完成；若不足，代码中有什么可观察状态、task、signal 或 queue 可作为更强的 ready/quiescent gate？

### B. 启动到主菜单期间的内存 mutation

对 SettingsSave、PrefsSave、ProgressState 分别回答：

1. load/deserialization 后、主菜单入口可用前，哪些 production 方法仍可能修改 live object？
2. mutation 是同步、awaited asynchronous、deferred、event/signal、platform callback、mod lifecycle callback 还是 frame/update 驱动？
3. mutation 是否立即保存、延迟保存、只设 dirty 状态，或仅在退出保存？
4. 哪些路径可能使 live state 暂时比 disk 新，足以解释“一次 session 中 Candidate A 不等、另一次相等”？只能列有调用点证据的候选，并标记是否可到达；不得把候选写成历史根因。

调查应从已知 manager/save mutation 方法反向查 caller，并从 production bootstrap/main-menu sequence 正向追踪；达到闭合的相关调用集后停止，不做无界全程序集 catalog。

### C. Save/write 调度与 pending work

1. Settings、Prefs、Progress 的所有相关 Save 方法返回 `void`、`Task` 或其他 awaitable 中的哪一种？底层 `WriteFileAsync`/backup/rename 流程如何串联？
2. 启动和主菜单路径上的 caller 是否等待完成；哪些 caller 丢弃 task、使用 continuation、queue/deferred call 或全局 task tracker？
3. 在安装全局 `SaveManager` override 前已经发起的真实-store write，是否捕获原 manager/store 引用并可能在 override 后完成？
4. 在恢复原 manager 后，isolated manager 发起但未完成的 task 是否可能越过 teardown？本任务只给静态风险，不运行验证。
5. 是否存在可查询的 pending-save counter/task set、flush API、idle signal 或其他确定性 barrier？若不存在，明确写 Unknown，不发明 quiet-frame 规则。

### D. 正常退出的三个 mtime 变化

1. 正常退出调用链中，哪些方法保存 Settings、Prefs、Progress 或创建/替换 `.backup`？
2. 哪条路径能解释“primary 或 backup 内容 hash 不变但 mtime 更新”？区分 overwrite、temp-write+rename、backup copy 和仅 metadata touch。
3. 这些写入是 baseline production behavior、mod unload behavior 还是无法从静态调用图区分？
4. 下一运行实验应如何设置 control/audit，才能将正常启动/退出写入与 transaction 内或延迟越界写入分开？

### E. 下一实验的 go/revise/stop 判定

报告必须在下列三项中只选一项：

- `GO_LIVE_SEEDED_SENTINEL`：存在可证实的 snapshot boundary，且可等待/审计所有相关 pending production writers；建议用 Candidate B 取代 disk rehydration。
- `REVISE_WITH_TIMING_GATE`：live-seeded 构造仍可保留，但必须先做一个不安装 override、不调用 progress 方法的更窄 runtime timing/barrier probe。
- `STOP_TRANSACTION_CANDIDATE`：存在无法约束或观察、会跨越全局 override/teardown 的真实-store writer，使该候选不满足 fail-closed 实验要求。

选择必须列出方法体/调用者证据、仍未知项和为什么另外两项不成立。不得在本任务中编写或运行下一 probe。
