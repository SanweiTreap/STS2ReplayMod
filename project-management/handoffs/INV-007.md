## 必须回答的问题

### 1. 拆分聚合失败点

逐项列出 `DirectWriteTransaction.cs` 中所有会产生 `BlockedPrecondition + RunState` 的条件，并按执行顺序标明：

- 它发生在 setup 前、scene/load 中还是 load 后；
- 它检查 production 必要条件、fixture 身份，还是仅为 probe 诊断便利；
- 静态证据能否证明它在固定 fixture/调用链上应成立；
- 若不成立，会否真的使 `UpdateProgressAfterCombatWon(player, room)` 或 `SaveProgressFile()` 的目标无效。

不得把“用户看见战斗画面”直接等同于某一具体断言通过。

### 2. 对照 production caller 与既有成功 setup

对照以下三条路径的精确顺序和对象来源：

- 006B 的 `SetUpReplay → Launch → NRun.Create → GenerateMap → LoadIntoLatestMapCoord`；
- 003A Phase B 已到达正常观看/Stop 的 setup；
- 官方 `NMultiplayerTest.RunReplay` caller。

特别检查：`RunState.FromSerializable`、`PreFinishedRoom`、`CurrentRoom`、`CombatRoom.Encounter`、`CombatState.Encounter`、`SpawnedEnemies`、`DebugOnlyGetState`、`ShouldSave` 以及等待 `ActionExecutor.IsPaused`/frame 的时点。所有结论必须固定到 v0.111.0 符号/IL。

### 3. 追踪两个 direct progress 方法的真实前置条件

静态追踪 `SaveManager.UpdateProgressAfterCombatWon(player, room)` 与 `SaveProgressFile()` 及其直接读取字段，形成最小参数/状态契约。明确哪些 006B 断言不是这两个方法所必需，尤其不得为了 fixture 身份验证而把不影响 progress mutation 的 encounter 对象引用一致、敌人生成数量或具体怪物 ID 自动升级为调用前置条件。

同时检查 006B 中已计算但可能未进入最终判定的变量或遗漏条件；只报告事实与影响，不修改源码。

报告只能选择一个：

- `READY_NEW_SENTINEL`：静态证据足以给出新 ID/schema probe 的最小修订契约；或
