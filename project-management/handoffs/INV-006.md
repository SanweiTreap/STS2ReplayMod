## 必须回答的问题

### A. Production cloud barrier

1. `NGame.GameStartup` 如何创建、保存、轮询/await `DoCloudSync`？完成、fault、cancel 分别怎样处理？
2. `DoCloudSync` 如何选择 `OverwriteCloudWithLocal` 或 `SyncCloudToLocal`，内部按 account/profile/path 发起哪些层级的操作？只需描述调用结构，不枚举用户文件。
3. `CloudSaveStore` 与 `SteamRemoteSaveStore` 的 leaf `WriteFileAsync` fault 在哪一层被 catch/log/convert？outer task 最终为什么可以 `RanToCompletion`？
4. Steam Cloud 客户端关闭、remote storage unavailable 或 API call invalid 时，fixed game code是否仍可能发起 remote method；哪些结论来自 game IL，哪些只能来自 Steamworks 官方契约，哪些仍 Unknown？
5. 对“startup cloud work 已收束”而言，future probe 应观察 `GameStartupComplete`、某个 outer task、某个 store batch，还是 leaf tasks？必须选出 production-aligned 最小 barrier，不得要求所有内部容错 leaf task 成功，除非 production 本身这样要求。
6. 是否还需要任何 global store patch 才能证明 barrier；若不需要，明确建议删除该 instrumentation 面。

### B. Profile-scope-safe observation contract

设计契约，不实现代码。契约必须逐项规定：

1. sealed/enabled 检查必须是每个 prefix/continuation 的第一项，发生在访问 `__args`、转换 path、读取 payload、计算 length/hash 或分配 CallState 之前。
2. terminal classification 使用单次原子 transition；胜出后立即阻止新增事件、payload 处理和 continuation 记录，再从已封闭集合生成 artifact。
3. allowed scope 仅为三个精确域：account selector、profile1 subtree、machine settings。说明 path canonicalization、separator、case、`..`、rooted path、URI-style path 与 symlink/reparse 风险如何 fail closed。
4. 如果必须读取第一个 path 参数做 scope 判定，判定不得持久化原字符串。non-allowed 结果立即 return；不得读取第二个参数，不得计算 payload length/hash，不得保留 profile token，不得产生 per-profile count。
5. 评估 future timing gate 是否根本不需要 payload hash。默认选择最少数据；仅当某一验收条件确实依赖 payload 时，才能为 allowed scope 说明必要性。
6. 对 allowed scope 的审计字段给出白名单；对 non-allowed invocation 给出“完全忽略”或单一全局布尔 `outOfScopeInvocationSeen` 二选一，并论证该布尔是否仍有必要。不得保留次数、operation、path、时间或 payload 派生值。
7. 已注册 async continuation 在 seal 后执行时必须 fast-return；CallState 不得提前缓存未获 scope authorization 的 payload 派生信息。
8. artifact 写入失败、并发事件与 terminal 同时发生、patch finalizer 异常时如何保持 fail closed。
9. 给出至少六个静态/unit-level negative cases：非 profile1 路径、伪前缀、路径穿越、rooted/URI path、seal 后 callback、payload getter/对象不得被访问。测试只使用合成字符串/对象，不使用真实存档。

### C. 旧 probe 的 precise failure analysis

只读源码并给出最小因果链：

- 哪一行/方法在 enabled/scope check 前处理 payload；
- 为什么 leaf fault 已知后审计仍继续；
- 为什么 `WriterAudit.Stop()` 仍不足以阻止后续 payload hashing；
- 当前 artifact 的 `FAIL_GATE` 为什么不能覆盖 Project Lead 的 `FAIL_SAFETY`；
- 哪些 design rule 必须进入新 probe，而不是简单移动一行代码后重试。

不得输出或引用任何越界 path/hash/count，报告只用“out-of-scope profiles/data”描述。
