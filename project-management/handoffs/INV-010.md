## 必须回答

### A. Capture driver 生命周期

- `ProbeTicker` 作为 `NGame` child 的 `_Process` 是否在 run/room scene 期间按 Godot/production 节点生命周期静态上应继续执行？
- `SetProcess(true)`、process mode、tree pause、scene replacement、node free/reparent 中哪些条件可停止它？
- R3 source/log 能排除哪些条件，哪些只能通过新运行 telemetry 确认？
- 比较 SPIKE-001A 中成功的 50ms async readiness poll，说明二者在 owner/task/node lifetime 上的差异。

### B. Readiness predicate 与异常面

逐项追踪固定 DLL 上：

- `RunManager.DebugOnlyGetState`、single player lookup、`PlayerCombatState`/Hand；
- `CombatManager.Instance`、`IsInProgress`、`IsOverOrEnding`、`IsPaused`、`PlayerActionsDisabled`、`IsPartOfPlayerTurn`；
- `PlayerTurnPhase.Play`；
- `ActionExecutor.IsRunning`、`IsPaused`、`CurrentlyRunningAction`；
- `NGame.CurrentRunNode`。

明确每项在第一回合可操作点的预期语义，特别验证 `ActionExecutor.IsRunning == false` 是否确实代表 action queue quiet。列出 `TryReadiness` 可能抛异常的具体访问点；不得把 catch-all null 当作已定位根因。

### C. Checkpoint 与 baseline 时点

追踪正常地图节点选择至：

1. room-before `current_run.save` 写入；
2. `PreFinishedRoom` 变为 null；
3. room push/enter；
4. combat setup；
5. 首回合 input-ready。

判断正式 checkpoint/protection baseline 应在何处原子封存。必须解决 R3 暴露的冲突：map 上旧 save 为 `PreFinishedRoom != null`，而等到 input-ready 才建 baseline 又漏掉 node-entry→readiness 窗口。

优先寻找只读观察点，例如 production `SaveRun`/`RunSaved` 完成、room entry 或 combat start 事件；不得建议 patch 掉写入、复制回存档、restore 或 rebaseline。

### D. 最小可观察 contract

若建议下一运行实验，必须预先定义：

- 全新 mod ID/schema/artifact/recovery identity；旧 001A2-R2 永不修改/重跑；
- arm 阶段等待人工点击时不超时；一旦检测到目标 production checkpoint write/room entry，启动有界 capture deadline；
- capture driver heartbeat（至少首次 combat tick、总 tick、最后 tick）；
- 每个 raw readiness 字段的状态变化与定期 bounded sample；
- catch 必须记录 exception type/message/site/count，不能静默返回 null；
- 30 quiet frames 的定义以及连续性被哪一字段打断；
- baseline 必须在 checkpoint 可验证后立即封存，早于 A snapshot；
- 若 deadline 到期，生成可审计 terminal artifact，而不是无限显示 Ready；
- 用户目标后立即停止、不出牌/End Turn/选择/领奖；
- profile1-only、Cloud、exact-mod-set 和保护边界；其他 profile 禁止访问。
