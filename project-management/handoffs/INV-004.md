## 必须回答的问题

### A. native recorder 与文件完整性

1. `CombatReplayWriter` 在何时开始、记录、flush/finalize 并替换 `latest.mcr`？
2. 哪些玩家动作、hook、resume、choice 会进入 `CombatReplay.events`；哪些明确不会？
3. 战斗胜利或 combat teardown 是否有“记录已完整”的标志、终止事件、计数或写盘时序？仅 `events>0` 是否不足以证明 fixture 覆盖到胜利？
4. 对固定 fixture 做只读事件清单：按顺序列出 event type、可安全展示的 action type/关键 ID、player、action/hook/choice ID；不得修改 fixture。
5. 结合用户原始操作与游戏日志，能否确定 11 个事件本来就只对应两个回合，还是 recorder/file finalization 丢失了后续动作？不能确定时明确写 Unknown。

### B. native debug replay caller 与 probe 调度差异

1. 从 v0.111 DLL 还原 `NMultiplayerTest.RunReplay` 的完整 setup、事件循环、等待和结束条件。
2. 与 `ReplayTransaction.DispatchReplayEvents` 逐项比较：每种 event 的处理、每次 enqueue 后的等待、end-turn readiness、action executor 完成语义、combat completion 等待、synchronizer 状态和 teardown。
3. 判断 Phase C 的事件耗尽是否可能来自 probe 与官方 debug caller 的语义差异；每个候选原因标记 Confirmed / Inferred / Unknown，并给出可证伪方法。
4. 不得把“第三回合停止”直接称为 replay divergence，除非状态或 checksum 证据支持；否则只描述为事件流未使战斗结束。

### C. direct-write sentinel 的最小解耦方案

比较至少以下候选，但最终只推荐一个：

- 使用经证明完整、可一击结束的 native combat fixture；
- 在有效 replay session 内由人工或受控游戏原生动作达成胜利；
- 在隔离 transaction 内以合法状态直接触发 production `UpdateProgressAfterCombatWon → SaveProgressFile` 调用链；
- 其他有方法体证据、且不 patch-away write 的更窄候选。

对每个候选说明：它究竟证明什么、不能证明什么、是否混入 replay reconstruction/dispatch 正确性、所需状态、潜在 side effect、可审计性和停止条件。

最终推荐必须允许后续工作包把两件事分开判定：

1. direct progress write 是否确实落入 isolated manager/store；
2. native replay 是否能完整、确定地重放到胜利。

若不存在足够可信且有界的隔离哨兵，明确 `BLOCKED_SENTINEL`，不要推荐“多换几个 fixture 试试”。
