# INV-002 Implementation Codex Handoff

状态：Ready  
发出日期：2026-08-27  
触发证据：`SPIKE-001A-report.md`

## 任务目标

只读追踪 STS2 public-beta `v0.111.0` 的正常 continue/load、RunState 生命周期、普通 save 写入及房间/战斗重建调用链，为下一次安全恢复实验选择正确边界和调用顺序。

本任务必须回答：为什么 SPIKE-001A 的候选链会改写普通 `current_run.save` 并重建出不同手牌/RNG；是否存在有方法体证据支持的官方卸载、隔离或房间前恢复入口。它不运行新的恢复实验。

## 必须回答的问题

1. 正常主菜单 Continue 从读取 `current_run.save` 到 `RunState` 建立、setup、room load 和 UI 切换的实际调用顺序是什么？
2. `RunManager.SetUpSavedSingleplayer` 内部或其下游哪个调用写入 `current_run.save`？为什么外部先设 `ShouldSave=false` 仍会写？是否存在参数、上下文或不同入口控制该写入？
3. `RunManager.State` 的所有权与生命周期是什么？正常流程如何结束/替换现有 state；是否有明确的 unload/reset/return-to-menu API，能解释同进程 `State is already set.`？
4. `SerializableRun.PreFinishedRoom`、`ToSave(CurrentRoom)` 和 `NGame.LoadRun` 的语义边界是什么？它们保存的是房间前状态、房间结果还是中途状态？
5. `LoadRun`/room setup 中哪些方法会创建战斗、洗牌、抽起手牌或消费 `Shuffle`/`Niche` RNG？能否用调用链解释 SPIKE-001A 的 14 项 diff？不能确认具体 RNG 调用者时明确标为 Unknown。
6. 游戏是否已有用于 replay/spectate/tutorial/debug 或多人的隔离运行上下文、非持久 profile/save provider、可替换存储层或 `shouldSave=false` 正确创建路径？符号存在不等于适用，需看方法体/调用者。
7. 基于证据，下一实验应优先验证哪一个且仅一个候选：
   - 房间前原生检查点 + 快速重演；
   - 官方隔离 run/profile 中的正常 continue；
   - 不同的卸载/setup/load 顺序；
   - 当前没有安全候选，需先调查状态序列化扩展。

## 明确非目标

- 不启动游戏，不按 F8/F9/F10，不运行任何恢复或写盘测试。
- 不修改、删除、回滚 ordinary save；不卸载 probe（由用户或 Project Lead 另行处理）。
- 不修改 SPIKE001A 源码，不实现拦截 save、替换 profile、Harmony patch 或自制快照。
- 不进入出牌 capture/dispatch，不解锁 SPIKE-001B。
- 不调查 UI 美术、完整场景、跨版本、多人、接管或 gameplay mod 兼容。
- 不把反编译中发现的旁支功能扩成新任务；只登记。
