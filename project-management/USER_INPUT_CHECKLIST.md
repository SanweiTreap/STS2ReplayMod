# 用户验证与信息清单

更新日期：2026-08-25

目的：把项目发起人的运行观察转化为可追踪证据。问题均带稳定编号；可以逐项回答，不要求一次完成。若某项无法测试，直接回答“无法测试 + 原因”，不要凭印象补全。

## 回答方式

建议按以下格式回复：

```text
A1：...
A2：...
证据：截图 / 日志文件 / 复现步骤 / 仅凭记忆
置信度：刚刚复测 / 以前测过 / 不确定
```

较大的日志、截图或 replay 文件可放入 `evidence/user-tests/<问题编号>/`。分享日志前可遮盖 Windows 用户名等无关个人信息；不要修改会影响错误判断的堆栈和版本信息。

## 第 1 轮：环境与版本身份（优先，无需重新玩完整对局）

### 信息 A：STS2 安装与版本

- **A1**：目前机器上可运行哪些游戏版本？正式版 v0.107、public-beta v0.111，还是其他版本？
- **A2**：游戏主菜单、日志或可执行文件中显示的完整版本字符串分别是什么？
- **A3**：你现在是否能方便地在正式版和 public-beta 之间切换？切换会不会覆盖模组、存档或配置？
- **A4**：游戏安装目录在哪里？如果不方便给绝对路径，只需说明是否为默认 Steam 目录。

需要的证据：版本界面截图或启动日志中的版本行优先。

### 信息 B：此前测试使用的 RunReplays 构建

- **B1**：此前在 v0.107 成功播放 sample replay 时，RunReplays 从哪里下载？GitHub release、Nexus、自己编译，还是其他来源？
- **B2**：安装目录中的 `RunReplays.json` 显示什么版本？
- **B3**：当时安装了哪些 RunReplays 文件（例如 DLL、PCK、JSON）？这些原文件现在是否还保留？
- **B4**：当时是否依赖 BaseLib？若是，BaseLib 的版本或来源是什么？
- **B5**：如果 DLL 仍在，是否可以复制到工作区供后续计算 hash 和比对？不要覆盖现有文件，可放到 `evidence/user-tests/B/`。

需要的证据：原始 manifest、DLL/PCK 文件或下载页名称。目标是把“v0.107 成功构建”绑定到明确 artifact。

### 信息 C：测试时的模组环境

- **C1**：除了 RunReplays 和它的必需依赖，当时还启用了哪些模组？
- **C2**：严重卡顿在只启用 RunReplays（及 BaseLib）时是否也出现？
- **C3**：RunReplays 是否开启 overlay、verbose/debug logging 或其他可配置选项？
- **C4**：游戏是否使用 modded profile，是否开启 Steam Cloud？

需要的证据：模组列表截图、配置文件或准确回忆。该信息用于排除其他模组和日志设置造成的干扰。

## 第 2 轮：已知行为的最小复现

### 信息 D：v0.107 sample replay 成功路径

- **D1**：从启动游戏到 sample replay 开始播放，完整点击路径是什么？
- **D2**：使用的是哪个 sample/seed/角色？大约能播放到哪一层？
- **D3**：是否能够从头自动播放到结束，还是只验证了部分楼层？
- **D4**：播放过程中是否观察到指令失败、等待过久、动画异常、状态偏离或错误日志？
- **D5**：相同步骤重复两次，结果是否一致？

建议证据：简短录屏、sample 名称、起止楼层、日志。无需为了本题重玩真实完整对局。

### 信息 E：播放控制语义

- **E1**：点击暂停后，哪些内容停止？command、动画、敌人行动、计时或所有游戏逻辑？
- **E2**：一次 Step 的单位是什么：一个 replay command、一个游戏 action、一个动画阶段，还是表现不稳定？
- **E3**：点击停止后停留在哪个状态，UI 是否恢复正常？
- **E4**：从当前位置接管后，能否正常打牌、选路、保存并继续？
- **E5**：接管后的对局是否写入 run history、统计或存档？有没有明显异常副作用？
- **E6**：接管前后是否存在无法关闭的 overlay、输入锁或 replay 状态残留？

建议证据：选择一个短 sample，分别执行暂停、Step、停止、接管，并记录每一步观察。

### 信息 F：真实录制的基本结果

- **F1**：RunReplays 是自动开始录制，还是需要手动开启？
- **F2**：replay 数据在什么时候写盘：每次操作、保存时、换层时，还是无法确定？
- **F3**：一次短对局生成哪些目录和文件？文件大小大约是多少？
- **F4**：自己录制的 replay 是否成功加载并播放过？成功覆盖过哪些场景？
- **F5**：是否遇到录制文件缺失、截断、重复 command 或无法解析？

建议证据：一段 2–3 层的短测试即可，保留生成文件和对应日志。

## 第 3 轮：性能问题定界

### 信息 G：卡顿的触发条件

- **G1**：卡顿发生在“打开地图”“点击节点”“进入房间”“保存”中的哪一步？
- **G2**：卡牌附近的卡顿发生在出牌瞬间、效果结算、抽牌、弃牌、回合结束还是战斗结束？
- **G3**：卡顿是单次长停顿、连续掉帧，还是随对局时间逐渐恶化？
- **G4**：暂停/关闭 RunReplays overlay 或 debug logging 后有无变化？
- **G5**：关闭 RunReplays、保留相同其他模组后，卡顿是否消失？
- **G6**：卡顿时 replay/log 目录是否出现大量新文件或文件尺寸快速增长？

建议先提供定性回答；暂时不需要安装 profiler。

### 信息 H：最小对照测试

尽量在同一游戏版本、同一画质和相近场景下测试：

1. 不启用任何模组。
2. 只启用 BaseLib（如需要）。
3. 启用 BaseLib + RunReplays，保持默认设置。
4. 启用 RunReplays，但关闭可关闭的 overlay/verbose logging。

每组回答：

- **H1**：平均体验是否流畅？
- **H2**：地图点击时最长停顿大约是 `<0.1s / 0.1–0.5s / 0.5–2s / >2s` 中哪档？
- **H3**：打出一张简单攻击牌时是否出现可感知停顿？
- **H4**：连续游玩若干层后是否明显恶化？大约从第几层开始？
- **H5**：测试结束后的 replay/log 文件数量和总大小是多少？

这里先求稳定复现和数量级，不要求精确 benchmark。正式 profiling 会由后续 PERF-001 单独定义。

## 第 4 轮：public-beta v0.111 兼容性

需要的证据：未经截断的首个异常、stack trace、游戏版本和 RunReplays artifact。后续连锁异常可以暂缓。

## 第 5 轮：MVP 产品选择

这些不是技术事实，没有“正确答案”；可以在前几轮调查后再回答。

### 信息 L：首版支持边界

- **L1**：首个版本应优先支持当前正式版，还是 public-beta？

## 推荐回答顺序

1. 先回答 A、B、C，建立环境身份。
2. 再做 D、E、F 的短复现。
3. 确认卡顿仍可复现后做 G、H。
4. 有完整日志时回答 I。
5. 技术约束更清楚后再决定 J、K、L。

不需要等待整个清单完成。每收到一组回答，Project Lead 应将其写入调查台账，并判断是否改变后续任务顺序。

### 2026-08-25 — K5（主策略已回答）

- **K5 产品倾向**：采用更“硬”的记录方式，保存更多权威状态，尽量从记录层避免 divergence。
- **可恢复偏差**：自动用记录状态覆盖/恢复并继续播放，同时输出错误日志；不默认停下来要求玩家选择。
- **可能根因判断**：实现缺陷，或跨版本/卡牌变更等内容兼容问题。该判断是合理分类，不代表只存在这两种根因。
- **技术边界**：强记录不自动保证任意跨版本恢复；缺失类型/资源、破坏性 schema 变化和文件损坏可能不可恢复。
- **待确认**：记录状态本身无法装载或恢复时，是否接受停止播放并显示明确错误作为最终兜底。

### 2026-08-25 — K5 完成 / L1–L2

- **K5 兜底已回答**：权威状态本身无法读取或恢复时，接受停止播放并显示明确错误。

### 2026-08-25 — L3

- **L3 已回答**：MVP 正式保证原版内容、Replay Mod 及必要依赖；其他 gameplay mod 正式兼容延期。
- Replay 始终记录全部启用模组和版本；录制/播放 gameplay mod 环境不一致时明确警告或拒绝，不静默播放。
- 纯 UI/外观模组尽力兼容但不作首版保证；若实际影响状态或 hook，则不能继续按“纯外观”处理。
- 后续 gameplay mod 支持应作为兼容协议/专项验证推进，不默认逐个硬编码。

### 2026-08-25 — L4

- **L4 已回答**：MVP 支持 replay 文件分享到另一台机器，并在匹配环境中导入/播放。
- 匹配环境至少要求相同精确游戏构建、兼容的 Replay 格式与 Replay Mod 版本，以及相同 gameplay mod 集合/版本；不匹配时明确诊断，不强制播放。
- 管理页提供导入入口；外部 replay 作为不可信数据校验格式、schema、完整性、大小和环境元数据，禁止嵌入代码执行、任意路径写入、路径穿越和静默覆盖。
- Replay 默认不得包含分享所不需要的本机绝对路径、Windows 用户名等本地身份信息。
- 本决定不扩大为跨版本或缺失 gameplay mod 环境的兼容承诺。

### 2026-08-25 — L5

- **L5 已回答**：MVP 后大型方向优先级为 `多人 Replay → 跨版本播放 → 隔离的可游玩 Replay 分支 → 其他 gameplay mod 正式兼容`。
- 项目发起人明确指出，多人是这些方向中最重要的。
- 边界：多人仍不属于当前单人 MVP；该排序决定 MVP 后战略方向，不允许当前 milestone 自行扩张。
- 原 L5 中的“真正 seek”已经由 K1a 纳入 MVP，因此本次排序改用尚未进入 MVP 的“隔离可游玩分支”替代。
- **第五轮状态**：J、K、L 全部完成；下一步由 Project Lead 收束 MVP 玩家闭环和验收表。
